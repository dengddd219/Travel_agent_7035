# 陪伴 Agent 说明指南

> 面向 PPT 讲解的结构化参考文档。总-分-总框架，三维度互斥并列。

---

## 一、总论：为什么要做陪伴 Agent？

旅行规划 Agent（主 Agent）解决的是**出发前**的问题——生成一份多日行程。但旅行当天，用户面对的是完全不同的挑战：

> 行程已定，现实在变。天气突变、景区关门、体力不支、迷路、找餐厅……这些问题无法在出发前预判，主 Agent 无力应对。

**陪伴 Agent 的存在价值：将 AI 辅助从"规划时"延伸到"出行中"。**

它不生成行程，它**守护行程的执行**。

## 二、整体框架：Agent 架构图

### 2.1 系统定位（三层架构）

```
┌─────────────────────────────────────────────────────┐
│                    用户（旅行当天）                     │
│         "附近哪里吃饭？" / "下雨了怎么办？"              │
│         "来不及了怎么办？" / "我迷路了！"                │
└──────────────────────┬──────────────────────────────┘
                       │ 自然语言输入
                       ▼
┌─────────────────────────────────────────────────────┐
│                  陪伴 Agent 核心                       │
│   ┌──────────┐  ┌──────────┐  ┌──────────────────┐  │
│   │ 意图路由  │→│ 行动规划  │→│   工具执行 + 验证  │  │
│   │ Router   │  │ Planner  │  │  Executor+Repair  │  │
│   └──────────┘  └──────────┘  └──────────────────┘  │
│                       │                              │
│              CompanionState（跨轮持久状态）             │
└──────────────┬──────────────────────────────────────┘
               │ 调用 8 个工具
               ▼
┌─────────────────────────────────────────────────────┐
│                    工具层（外部接口）                   │
│  resolve_location │ get_weather_now │ get_route      │
│  retrieve_candidates │ score_candidates              │
│  replan_itinerary │ resolve_emergency_resources      │
│  get_poi_detail                                      │
└─────────────────────────────────────────────────────┘
```

### 2.2 Agent 内部执行流（单轮）

```
用户输入
    │
    ▼
[1] 约束提取           ← 解析"老人/不爱走路/不吃辣"等结构化信息
    │
    ▼
[2] 意图路由（Router） ← LLM 语义分类：emergency / replan / coordinate / search
    │
    ├─ 有待处理任务？ → [TaskFlow] 确定性规则处理（无需 LLM）
    │
    ├─ LLM 可用？    → [3a] 行动规划（Planner）
    │                         │
    │                    [4] 工具执行（按计划逐步调用）
    │                         │
    │                    [5] 自检验证（time / weather / mobility / core_experience）
    │                         │
    │                  验证失败？→ [6] 修复规划（Repair Planner）
    │                         │
    │                    [7] 回复生成（Response Generator）
    │
    └─ LLM 不可用？  → [3b] 确定性 Fallback（本地规则引擎）

    ▼
结构化回复（**结论** / **依据** / **下一步**）
```

## 三、核心设计解构：三个互斥策略维度

三个维度彼此**互斥、并列、完整**，覆盖陪伴 Agent 所有核心设计决策。

---

### 维度一：意图识别策略——"先分类，再行动"

#### 问题

用户的一句话可能是求救、可能是改计划、可能是问路、可能是找吃的。同一套工具组合应对不同意图，效果会完全不同。如果跳过分类直接调工具，极易产生"用推荐餐厅的逻辑应对应急求救"的错误。

#### 解决思路

在工具调用之前，先用语义路由器（LLM 分类 + 规则兜底）明确意图类别，再根据类别决定工具策略和回复风格。

#### 四类意图（互斥完备）

| 意图 | 触发场景举例 | 响应策略 |
|---|---|---|
| `emergency` | 受伤、迷路、紧急求助、无法行走、手机没电 | 安全第一，先给回撤路径，再调 `resolve_emergency_resources` |
| `replan` | 天气变化、景区关门、时间不够、主动压缩行程 | 调 `replan_itinerary`，保留核心体验，说明调整原因 |
| `coordinate` | "来得及吗？""几点最晚出发？" | 调 `get_route` + `get_poi_detail`，给明确可行性结论 |
| `search` | 附近推荐、找餐厅、找替代点位、问本地问题 | 调 `retrieve_candidates` → `score_candidates` |

#### 关键设计决策

- 当 emergency vs search 不确定时，**强制选 emergency**——宁可多发安全提醒，不能漏掉真正求救
- 当 replan vs search 且已有 `remaining_plan` 时，**优先选 replan**——防止给推荐建议后用户自己修改，与已规划行程产生冲突

#### 验证结果

30 任务无 LLM 规则模式跑分：意图分类策略能被确定性规则完整复现（strict\_success=23.3%，avg\_rubric=50.1%），证明分类逻辑清晰、边界明确、不依赖黑箱 LLM 才能正确运行。

---

### 维度二：工具编排策略——"最少工具，完整覆盖"

#### 问题

调用越多工具，延迟越高、Token 消耗越大。但工具调用不足，LLM 会凭空捏造路线/天气/营业时间，产生"幻觉答复"——这在旅行场景中直接影响用户安全决策。

#### 解决思路

建立**工具使用硬规则（TOOL\_POLICY）**，以意图为入口，为每类场景规定必调工具组合，任何实时信息都必须先调工具再回答。

#### 工具层清单与分工（按功能互斥分组）

```
[位置解析组]
  resolve_location          ← 任何涉及地名的场景优先解析坐标，避免同名地点歧义

[推荐搜索组]
  retrieve_candidates       ← 候选 POI 召回（扩展 query，多维检索）
  score_candidates          ← 候选排序（结合用户 context 个性化打分）
  get_poi_detail            ← 单点详情（营业时间 / 票价 / 容量上限）

[路线时间组]
  get_route                 ← 实时路线 + 耗时（步行 / 打车两模式）
  check_time_feasibility    ← 纯时间可行性判断（确定性，无需 LLM）

[动态信息组]
  get_weather_now           ← 实时天气快照（触发 prefer_indoor 偏好更新）

[应急资源组]
  resolve_emergency_resources ← 医院 / 厕所 / 充电 / 网络 / 撤离路径

[行程重规划组]
  replan_itinerary          ← 剩余行程压缩 / 重排 / 保留 must_visit 核心体验
```

#### 关键设计决策

- 凡涉及实时信息（位置 / 天气 / 路线 / 营业时间），**先调工具再答**，LLM 不允许直接假设
- `retrieve_candidates` 后**必须跟 `score_candidates`**——召回和排序解耦，支持 party / budget / mobility 等 context 注入个性化排序
- 有 `remaining_plan` 时，用户要求改变行程**必须调 `replan_itinerary`**，禁止 LLM 直接编造新行程，防止新旧行程冲突
- 当前城市 `CompanionState.city` 作为所有地名解析的默认上下文，同名地点（如"春熙路/外滩"）不要求用户澄清城市

### 维度三：执行可靠性策略——"自检 + 修复 + Fallback"

#### 问题

LLM 驱动的 Agent 在工具结果异常、网络超时、输出格式错误时容易崩溃或产生错误答复。旅行场景容错要求极高，一次错误的应急建议可能导致真实安全风险。

#### 解决思路

在执行层加三道保障，构成**可靠性三角**：

```
[保障一] 自检验证（Self-Check）
  工具执行完成后，Planner 从四个维度审查输出质量：
  - time_budget       ：行程时间预算是否超支？
  - weather           ：天气是否影响计划执行？
  - mobility          ：团队行动能力是否匹配路线强度？
  - core_experience   ：必游 POI（must_visit）是否被保留？

[保障二] 修复规划（Repair Planner）
  自检发现问题时，启动 Repair Planner 针对性补救：
  - 重规划结果丢失核心体验   → 补调 retrieve_candidates 找替代景点
  - 天气/行动力移除太多景点  → 搜索室内/无障碍友好替代
  - 应急资源返回为空         → 扩大搜索范围或主动向用户澄清位置

[保障三] 确定性 Fallback（无 LLM 时）
  LLM 不可用或调用失败时，自动切换本地规则引擎：
  - 意图分类：正则 + 关键词规则（constraint_extractor）
  - 工具调用：TaskFlow 确定性任务流
  - 回复生成：模板化结构化输出
  保证系统在无网络 / 无 API Key 条件下仍可运行
```

#### 关键设计决策

- Fallback 不是降级，是**并行执行路径**——TaskFlow 优先于 LLM，部分场景规则比 LLM 更快更稳定
- `_ensure_structured_reply()` 强制所有输出格式为（**结论 / 依据 / 下一步**），避免 LLM 输出无结构散文，降低旅行中用户的认知负担
- LLM 调用失败时，`tool_logs` 中记录 `llm_fallback` 事件，前端可透明展示降级状态

## 四、业务成果

### 4.1 功能覆盖

| 场景类型 | 典型用户输入 | 覆盖状态 |
|---|---|---|
| 实时推荐 | "故宫附近哪里吃北京烤鸭？" | ✅ |
| 时间协调 | "现在去颐和园来得及吗？" | ✅ |
| 行程重规划 | "下雨了，把室外景点换掉" | ✅ |
| 应急处置 | "老人崴脚了，最近哪里能处理？" | ✅ |
| 无 LLM 离线运行 | 网络不稳或无 API Key | ✅ 规则降级 |

### 4.2 量化评测（VitaBench 风格）

- **测试集**：10 城市 × 3 任务 = 30 个任务（覆盖 replan / search / coordinate / emergency 四类意图）
- **无 LLM 确定性模式跑分**：
  - Strict Success Rate：**23.3%**（全部 rubric 项通过才算成功）
  - Avg Rubric Score：**50.1%**（细粒度打分，部分完成也计分）
- **评测维度**：时间合理性、必游地点保留、推荐相关性、应急资源有效性、澄清问题准确性

### 4.3 工程指标

| 指标 | 数值 |
|---|---|
| 支持城市 | 10 座（北京 / 上海 / 成都 / 重庆 / 广州 / 深圳 / 杭州 / 西安 / 厦门 / 南京） |
| Agent 工具数 | 8 个（覆盖位置 / 推荐 / 路线 / 天气 / 应急 / 重规划） |
| 执行路径数 | 3（LLM Agentic / TaskFlow / Deterministic Fallback） |
| 测试任务数 | 30（VitaBench 风格基准集） |
| Token 追踪 | 全程记录（companion_tracer + token_costing） |

## 五、总结：三段论收尾

**为什么做（Why）**：旅行当天的动态需求是主 Agent 无法覆盖的盲区，陪伴 Agent 补全了 AI 旅行助手的"最后一公里"。

**怎么做（How）**：以"意图识别 → 工具编排 → 执行可靠性"三层互斥策略为骨架，先分类再行动，先工具再回答，先自检再修复，确保每一轮回复都是可执行的结构化答复。

**做到了什么（What）**：在 10 城市 30 任务基准上完成首轮评测，搭建了完整的无 LLM 确定性测试通道，验证了架构在极端条件下的健壮性，为下一步全量 LLM 测评奠定了基础。

---

> **PPT 讲解提示**：三个维度建议用同一视觉语言（左 / 中 / 右三栏），强调它们是**同级并列、互斥覆盖、共同构成完整系统**的关系，而非先后顺序关系。每个维度内部遵循"问题 → 思路 → 行动 → 验证"的微叙事结构。
