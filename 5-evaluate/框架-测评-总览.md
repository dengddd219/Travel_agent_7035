## 1. 一句话总览

本项目的测评体系分为 **一块基础工程测评 + 三块核心业务测评**：

| 测评部分 | 测评对象 | 核心问题 | 主要指标 |
|---|---|---|---|
| 基础工程测评 | 整个 Agent 系统 | 系统是否稳定、快、成本可控 | 解决率、响应时间、错误率、Token/成本、A/B 指标 |
| RAG 测评 | 攻略知识检索与生成 | 检索是否准、回答是否忠实、有无幻觉 | Hit Rate、MRR、Faithfulness、Answer Relevancy、Context Precision |
| 主 Agent 测评 | 行前旅行规划 Agent | 是否理解需求，并生成合理行程 | 意图理解准确率、行程结构通过率、内容质量评分 |
| 陪伴 Agent 测评 | 旅行中动态陪伴 Agent | 是否能在现场多轮任务中做对决策 | strict success rate、rubric score、tool success、Avg@k / Pass@k |

---

## 2. 整体测评逻辑

旅行 Agent 不是普通问答系统，不能只看“最后一句回答好不好”。完整测评要同时覆盖三层：

1. **基础稳定性**：系统能不能稳定运行，响应是否足够快，成本是否可控。
2. **知识可靠性**：RAG 是否能召回正确攻略信息，并让回答基于证据。
3. **Agent 任务能力**：Agent 是否能理解用户目标、正确调用工具、完成旅行规划或现场陪伴任务。

可以概括为：

```text
基础工程指标
    ↓
RAG 知识质量
    ↓
主 Agent 行前规划能力
    ↓
陪伴 Agent 旅行中动态执行能力
```

---

## 3. 基础工程测评

### 测什么

基础工程测评是横向指标，不只属于某一个 Agent，而是覆盖整个系统运行表现。

### 核心指标

| 指标 | 含义 | 用途 |
|---|---|---|
| 解决率 | 用户任务是否被完成 | 判断整体业务有效性 |
| 响应时间 | 从输入到输出的端到端耗时 | 判断用户体验和线上可用性 |
| 错误率 | 异常、超时、工具失败比例 | 判断系统稳定性 |
| Token / 成本 | 单次任务消耗的模型资源 | 判断线上成本是否可控 |
| A/B 测试 | 对比不同策略或版本 | 判断改动是否真的带来收益 |

### 落地方式

- 在线 tracing：记录每次运行的延迟、token、工具调用、异常。
- 阈值告警：例如延迟过高、token 超限、工具循环调用。
- A/B 对比：比较不同 RAG 策略、prompt、planner 版本的效果。

---

## 4. RAG 测评

### 测什么

RAG 测评关注攻略知识系统是否能为 Agent 提供可靠信息，核心不是“生成得像不像”，而是：

- 是否检索到正确内容；
- 回答是否基于检索证据；
- 是否减少幻觉；
- 是否能支持后续行程规划。

### 主要维度

| 维度 | 指标 | 说明 |
|---|---|---|
| 检索准确性 | Hit Rate、MRR | 正确 chunk 是否被召回，排序是否靠前 |
| 忠实性 | Faithfulness | 回答是否忠于上下文 |
| 相关性 | Answer Relevancy | 回答是否贴合用户 query |
| 上下文精度 | Context Precision | 检索内容是否真正有用 |

### PPT 表达重点

RAG 是主 Agent 的知识底座。RAG 测不好，后面的行程规划就可能出现“看似合理但没有攻略依据”的问题。

---

## 5. 主 Agent 测评

### 测什么

主 Agent 负责行前规划，测评重点是它能否从用户需求出发，生成结构完整、路线合理、符合偏好的旅行计划。

### 三层测评结构

| 层次 | 测评内容 | 判断方式 |
|---|---|---|
| 层次一：意图理解 | 城市、天数、预算、偏好、同行人等槽位是否提取正确 | 规则匹配 / Golden cases |
| 层次二：行程结构 | 天数、每日安排、景点顺序、餐饮交通等是否完整合理 | 结构化断言 |
| 层次三：内容质量 | 主题匹配度、路线合理性、本地化程度、偏好满足率 | LLM-as-Judge + Rubric |

### PPT 表达重点

主 Agent 测评不是只看“有没有生成行程”，而是分层检查：

- 先看是否理解对；
- 再看结构是否完整；
- 最后看内容是否真正好用。

---

## 6. 陪伴 Agent 测评

### 测什么

陪伴 Agent 面向旅行中场景，任务更动态，需要在多轮对话中结合当前位置、天气、时间、用户状态和工具结果做决策。

### 测评思路

采用 VitaBench-style 轨迹评测：

- 构造旅行现场任务；
- 模拟用户与工具环境；
- 让 Agent 完成多轮任务；
- 记录完整轨迹；
- 用 rubric checklist 和 judge 判断任务是否完成。

### 主要指标

| 指标 | 含义 |
|---|---|
| strict_success_rate | 严格任务完成率 |
| avg_rubric_score | Rubric 平均得分 |
| avg_tool_success | 必要工具调用是否成功 |
| dimension_scores | reasoning、tool、interaction 等分维度得分 |
| Avg@k / Pass@k | 多次运行下的稳定完成能力 |

### PPT 表达重点

陪伴 Agent 的风险点不在“会不会聊天”，而在“旅行现场能不能做对”。所以必须看完整轨迹，而不是只看最后一句回复。

---

## 7. 四块测评之间的关系

| 层级 | 作用 | 失败时说明什么 |
|---|---|---|
| 基础工程测评 | 保证系统可运行、可上线 | 系统慢、不稳定、成本高 |
| RAG 测评 | 保证知识来源可靠 | 攻略召回不准、回答无依据 |
| 主 Agent 测评 | 保证行前规划质量 | 需求理解错、路线不合理、内容空泛 |
| 陪伴 Agent 测评 | 保证旅行中动态执行能力 | 多轮任务失败、工具调用错、现场决策差 |

整体上，基础工程测评是底座，RAG 测评保证知识质量，主 Agent 测评保证行前规划，陪伴 Agent 测评保证旅行中动态服务。

## 8. PPT 建议页结构

### 第 1 页：测评体系总览

- 一块基础工程测评 + 三块核心业务测评。
- 用一张表展示：基础、RAG、主 Agent、陪伴 Agent。

### 第 2 页：为什么不能只看最终回答

- Agent 有长流程、工具调用、知识检索、多轮决策。
- 所以要同时看响应质量、轨迹、RAG 证据和工程指标。

### 第 3 页：基础工程测评

- 解决率、响应时间、错误率、Token/成本、A/B。
- 说明这些指标保障系统上线稳定性。

### 第 4 页：RAG 测评

- 检索：Hit Rate、MRR。
- 生成：Faithfulness、Answer Relevancy、Context Precision。
- 说明 RAG 是知识可靠性的底座。

### 第 5 页：主 Agent 测评

- 意图理解。
- 行程结构验证。
- 内容质量 LLM Judge。

### 第 6 页：陪伴 Agent 测评

- 多轮任务仿真。
- 工具轨迹评测。
- Rubric + Avg@k / Pass@k。

### 第 7 页：总结

- 基础工程指标保证“能稳定跑”。
- RAG 保证“信息有依据”。
- 主 Agent 保证“行前计划做得好”。
- 陪伴 Agent 保证“旅行现场能动态处理问题”。
