# Travel_agent_7035 项目总体框架

> 适用场景：用于汇报或快速理解整个项目从数据、知识库、Agent 编排、前端呈现到最终评估的完整链路。

## 1. 一句话总览

本项目是一个面向旅行场景的双 Agent 系统：

- **主 Agent** 负责行前规划：把用户自然语言需求转成结构化画像，结合攻略 RAG、POI、天气、费用和酒店工具，生成多日行程、Markdown 报告和地图可视化数据。
- **陪伴 Agent** 负责旅行中支持：在用户实际出行时处理临时变更、附近搜索、路线判断、天气扰动、时间不足、应急资源等动态问题。
- **评估体系** 覆盖知识检索、生成质量、主 Agent 规划质量、陪伴 Agent 轨迹质量和系统工程指标，形成可持续迭代闭环。

## 4. 数据层：从原始笔记到结构化知识

### 4.1 原始数据

`0-data/` 保存按城市划分的旅行笔记，每篇是 Markdown 文件，通常包含 YAML frontmatter 和正文攻略内容。

数据特点：

- 来源偏真实用户经验，适合补充“本地玩法、避坑、路线经验”。
- 内容非结构化，需要通过切块和 metadata 组织成 RAG 知识。
- 城市覆盖主项目支持城市，例如 Beijing / Chengdu / Shanghai / Xian 等。

### 4.2 城市基础数据

`3-travel_planner/travel_planner/data/city_profiles/{city}.json` 提供城市级静态画像，例如：

- 城市别名和基础信息；
- 区域、交通、预算、旅行建议；
- seed POI fallback 数据；
- 当外部 POI API 不可用时，作为本地兜底。

### 4.3 外部实时数据

系统还接入或封装了多类外部信息：

| 数据类型 | 来源 | 用途 |
|---|---|---|
| POI / 地理编码 | 高德、Nominatim、本地 seed POI | 搜索景点、坐标、地图展示 |
| 天气 | C 组 weather API / 高德天气 | 行程天气提示、室内外调整 |
| 费用 | C 组静态费用表 | 预算估计、成本卡片 |
| 酒店 | C 组酒店 API / Playwright 携程 | 住宿推荐 |
| 实时 tips | Tavily / 启发式 fallback | 补充旅行建议 |

设计原则：每类外部数据都有 fallback，保证在 API 不稳定或离线时仍能跑通核心流程。

## 5. RAG 知识层

### 5.1 离线入库流程

`1-rag_pipeline_delivery/` 负责把原始笔记变成可检索知识：

```text
Markdown 文档
    ↓
读取 frontmatter + 正文
    ↓
清洗文本
    ↓
按地点标记和 recursive splitter 切块
    ↓
生成 embedding
    ↓
写入 ChromaDB
    ↓
构建 BM25 pickle
```

当前配置重点：

- chunk size 约 300；
- embedding 支持 OpenAI `text-embedding-3-small` 或本地 `BAAI/bge-small-zh-v1.5`；
- 同时保留 dense 向量检索和 BM25 关键词检索。

### 5.2 在线检索流程

`2-rag-retrival/search_notes.py` 提供统一入口：

```python
search_notes(query, city="", category="", strategy="hybrid", top_k=5)
```

三种策略：

| strategy | 逻辑 | 使用场景 |
|---|---|---|
| `hybrid` | ChromaDB dense + BM25，再做 RRF 融合 | 默认策略 |
| `dense` | 纯向量检索 | 语义查询 |
| `filter` | 先 metadata 过滤，再向量检索 | 城市/类别明确时 |

当 ChromaDB 不可用时，系统自动退化为 BM25。

### 5.3 Agent 侧 RAG 适配

主 Agent 不直接使用原始 chunk，而是通过 `strategy_rag_adapter.py` 做结构化提取：

- `recommended_pois`
- `theme_suggestions`
- `local_pitfalls`
- `neighborhood_notes`
- `evidence_chunks`
- `route_pair_hints`
- `poi_roles`
- `pitfall_evidence`

这层的作用是把“攻略文本”变成 planner 能理解的证据层，支持后续路线、主题、避坑和本地化表达。

## 6. 主 Agent：行前规划链路

### 6.1 入口

用户通过前端或 API 调用：

```text
POST /api/chat
```

后端入口：

```text
backend/server.py
    → TravelPlanningAgent.start_conversation()
    → TravelPlanningAgent.continue_conversation()
```

### 6.2 用户画像提取

主 Agent 先把自然语言转成结构化 `UserPreferences`：

```text
city
start_date
trip_days
travel_type
budget_level
pace
interests
must_visit
avoid
```

关键逻辑：

- 城市支持中英文别名；
- 可识别预算、节奏、亲子/美食/休闲/主题等旅行类型；
- 多轮对话通过 `preference_memory` 合并增量修改；
- `avoid` 优先级高于 `must_visit`。

### 6.3 多工具编排

主 Agent 使用工具调用收集规划所需上下文：

| 工具 | 来源 | 作用 |
|---|---|---|
| `get_city_context()` | 城市 JSON | 城市基础画像 |
| `get_strategy_context()` | RAG | 攻略证据、路线建议、避坑 |
| `search_batch_pois()` | 高德 / Nominatim / seed POI | 搜索 POI 与坐标 |
| `get_weather_forecast()` | C 组天气 API | 多日天气 |
| `get_cost_summary()` | C 组费用 API | 预算估算 |
| `get_travel_tips()` | Tavily / fallback | 通用旅行 tips |
| `get_hotel_candidates()` | C 组酒店 API | 酒店候选 |

### 6.4 确定性规划器

规划核心不是让 LLM 直接写完整行程，而是交给 Python planner：

```text
planner.py
    ├─ _select_pois()
    ├─ _allocate_days()
    ├─ route ordering / TSP
    └─ review_itinerary()
```

这样设计的原因：

- 可复现；
- 可调试；
- 可审计；
- 可以用规则验证结构质量；
- 避免 LLM 随机生成路线。

### 6.5 输出结果

主 Agent 最终返回：

```text
ChatResponse
    ├─ report                  Markdown 行程报告
    ├─ itinerary_json          结构化行程
    ├─ map_payload             高德地图渲染数据
    ├─ hotel_recommendations   酒店推荐
    └─ tool_logs               工具调用轨迹
```

## 7. 陪伴 Agent：旅行中动态执行链路

### 7.1 入口与定位

陪伴 Agent 通过：

```text
POST /api/companion
```

它处理的是用户已经在旅行中的问题，例如：

- 时间不够，需要压缩剩余行程；
- 下雨，需要换室内方案；
- 老人或小孩走不动；
- 赶车、赶预约、闭馆风险；
- 附近吃饭、咖啡、休息点；
- 厕所、医院、走失、手机没电等应急场景。

### 7.2 CompanionState

陪伴 Agent 使用 `CompanionState` 维护旅行中状态：

```text
city
current_location
remaining_plan
completed_pois
skipped_pois
party
constraints
preferences
turn_history
pending_task
```

这使它不是一次性问答，而是有上下文、有状态、有任务延续的现场 Agent。

### 7.3 意图路由

陪伴 Agent 将用户输入分成四类核心意图：

| 意图 | 典型场景 | 工具策略 |
|---|---|---|
| `replan` | 时间不够、下雨、景点关闭、想改行程 | `replan_itinerary`，必要时补 route/weather |
| `search` | 找附近餐厅、咖啡、休息点、替代 POI | `retrieve_candidates` → `score_candidates` |
| `coordinate` | 来不来得及、几点出发、路线可行性 | `get_route` + `get_poi_detail` |
| `emergency` | 厕所、医院、走失、手机没电、身体不适 | `resolve_emergency_resources` |

安全优先级：当 emergency 和其他意图冲突时，优先按 emergency 处理。

### 7.4 执行可靠性

陪伴 Agent 不是只靠 LLM 生成答复，而是包含：

- Router：识别意图；
- Planner：决定工具调用；
- Executor：执行工具；
- Self-check：检查时间、天气、行动力、核心体验；
- Repair：发现问题后修复计划；
- Fallback：LLM 不可用时走本地确定性规则。

当前 full LLM benchmark 显示，陪伴 Agent 的主要短板集中在工具闭环，例如 `get_route`、`replan_itinerary`、时间 buffer 校验不稳定。

## 9. 评估体系：从知识到 Agent 轨迹

评估放在 `5-evaluate/`，不是单一指标，而是分层评估。

### 9.1 总体评估结构

```text
基础工程评估
    ↓
RAG 检索评估
    ↓
RAGAS 生成质量评估
    ↓
主 Agent 行前规划评估
    ↓
陪伴 Agent 旅行中轨迹评估
```

### 9.2 RAG 检索评估

目标：验证知识库是否能召回正确攻略内容。

核心指标：

| 指标 | 含义 | 当前结果 |
|---|---|---:|
| HR@5 | Top 5 是否命中正确内容 | 93.5% |
| MRR | 正确结果平均排名质量 | 0.98 |

位置：

- `1-rag_pipeline_delivery/rag/evaluate.py`
- `5-evaluate/eval_dashboard.html`

### 9.3 RAGAS 生成质量评估

目标：验证基于 RAG 的回答是否忠实、相关、上下文有效。

当前结果：

| 指标 | 当前结果 |
|---|---:|
| case count | 100 |
| faithfulness | 0.9526 |
| answer relevancy | 0.8860 |
| context precision | 0.7419 |
| overall | 0.8602 |

位置：

- `5-evaluate/golden_cases.json`
- `5-evaluate/ragas_evaluator.py`
- `5-evaluate/ragas_result.json`

### 9.4 主 Agent 三层评估

主 Agent 评估不是只看最后报告，而是三层递进：

| 层级 | 测什么 | 方法 | 当前状态 |
|---|---|---|---|
| Layer 1 | 意图理解和槽位提取 | Golden cases 规则比对 | `test_intent_understanding.json` 已有 110 cases，待全量跑分 |
| Layer 2 | 行程结构硬约束 | Python 结构化断言 | 单个 Beijing 样例全 PASS |
| Layer 3 | 内容质量 | LLM Judge 四维打分 | 脚本已建，当前 Azure `api-version` 配置需修 |

四个内容质量维度：

- 主题匹配度；
- 路线合理性；
- 内容本地化程度；
- 用户偏好满足率。

位置：

- `5-evaluate/eval_main_agent.py`
- `5-evaluate/eval_layer1_intent.py`
- `5-evaluate/eval_layer2_structure.py`
- `5-evaluate/eval_layer3_content.py`
- `5-evaluate/main_agent_runs/`

### 9.5 陪伴 Agent 轨迹评估

陪伴 Agent 用 VitaBench-style 轨迹评测：

```text
任务集
    ↓
用户模拟器 rule / llm
    ↓
Companion Agent 多轮执行
    ↓
记录 trajectories.jsonl
    ↓
Rule / Hybrid evaluator
    ↓
summary + dashboard + bad cases
```

当前 benchmark：

| 指标 | Offline Rule Baseline | Full LLM Benchmark |
|---|---:|---:|
| 任务规模 | 30 tasks x 1 trial | 30 tasks x 4 trials = 120 trials |
| Strict Success | 23.3% | 30.0% |
| Avg Rubric | 50.1% | 55.3% |
| Avg Tool Success | 31.7% | 36.2% |
| Avg@4 | - | 30.0% |
| Pass@4 | - | 36.7% |
| Pass^4 | - | 23.3% |

三维得分：

| 维度 | 得分 |
|---|---:|
| reasoning | 65.4% |
| tool | 36.7% |
| interaction | 69.2% |

主要失败原因：

- `missed_deadline`
- `weather_guess`
- `no_route_check`
- `overpacked_plan`
- `drops_core_interest`
- `keeps_bad_weather_outdoor`

位置：

- `5-evaluate/companion_eval_pipeline.py`
- `5-evaluate/companion_tasks_10_cities.json`
- `5-evaluate/companion_eval_runs/full_llm_k4_merged/summary.json`

## 10. Tracing 与看板

### 10.1 在线 tracing

系统会记录关键运行轨迹，便于后续复盘：

| Trace | 位置 | 内容 |
|---|---|---|

## 11. 项目价值闭环

这个项目不是“生成一份行程”这么简单，而是建立了一个完整闭环：

```text
真实旅行笔记数据
    ↓
可检索知识库
    ↓
可解释的工具编排
    ↓
可复现的确定性规划器
    ↓
可交互的地图和报告前端
    ↓
旅行中动态陪伴 Agent
    ↓
可量化评估和 bad case 定位
    ↓
下一轮代码 / prompt / 工具策略优化
```

其中最重要的工程思想是：

- RAG 负责提供有依据的旅行知识；
- LLM 负责理解、编排和表达；
- Python planner 负责可复现的行程结构；
- 工具层负责实时世界信息；
- Evaluation 负责把“感觉好不好”变成可追踪指标。

## 14. 汇报时的推荐讲法

### 14.1 一页讲清项目

```text
我们做的是一个双 Agent 旅行系统。
主 Agent 解决出发前怎么规划，陪伴 Agent 解决旅行中怎么动态调整。
底层用小红书攻略构建 RAG 知识库，中间用工具编排和确定性 planner 生成可解释行程，前端用 Markdown + 地图展示，最后用 RAGAS、主 Agent 三层评估和 Companion 轨迹评估形成闭环。
```

### 14.2 一页讲清技术链路

```text
数据层：0-data 原始攻略 + city profiles + 外部 API
知识层：ChromaDB + BM25 hybrid RAG
Agent 层：主 Agent 工具编排 + Python planner；陪伴 Agent router/planner/executor/repair
产品层：FastAPI + chat UI + 高德地图
评估层：RAG HR/MRR + RAGAS + 主 Agent 三层评估 + Companion 轨迹 benchmark
```

### 14.3 一页讲清评估结果

```text
RAG 检索：HR@5=93.5%，MRR=0.98
RAGAS：100 cases overall=0.8602
Companion：120 trials full LLM，strict=30.0%，rubric=55.3%，tool=36.2%
结论：知识检索和生成质量已经较强，当前最大优化空间在 Companion 的工具闭环和现场约束落地。
```
