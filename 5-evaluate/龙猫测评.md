## 原始笔记（VitaBench 论文解读）

---

我看完了。你说的 ATO 我理解是论文里的 **OTA（Online Travel Agency）**。这篇 VitaBench 的核心评测方法可以概括成一句话：

它不是只看最终答案，而是让 agent 在“模拟用户 + 工具 API + 数据库”的真实任务环境里跑完整轨迹，然后用 **rubric checklist + 滑动窗口 LLM judge** 判断每个原子目标是否完成，再用多次运行指标衡量成功率和稳定性。

来源：本地 PDF、[arXiv 论文页](https://arxiv.org/abs/2509.26490)、[VitaBench 官网](https://vitabench.github.io/)。

**论文里的评测框架**

1. **三维复杂度不是简单三项打分，而是任务设计和诊断框架**
   
   它把 agent 任务复杂度拆成：
   
   - **Reasoning complexity**：是否要整合时间、空间、用户偏好、历史行为、隐含约束。
   - **Tool complexity**：工具数量、工具依赖、前置条件、后置条件、跨工具链路。
   - **Interaction complexity**：多轮对话、用户信息逐步暴露、用户性格、主动澄清能力。

   对你的 travel agent 来说，可以把任务难度分层设计成：单一重排任务、带天气/距离约束的任务、跨酒店/景点/交通/突发情况的复合任务。

2. **任务不是单条 prompt，而是完整环境**
   
   每个任务包含：
   
   - user profile：年龄、常住地、饮食禁忌、性格等。
   - instructions：用户真实需求，包含显性和隐性约束。
   - environment：天气、地点、酒店、景点、车票、历史订单等。
   - tools：可调用 API，并带 pre-condition / post-condition。
   - rubrics：原子评测标准。

   你本地的 `longcat/vitabench/data/vita/domains/ota/tasks.json` 已经很接近这个结构：100 个 OTA 任务，`evaluation_criteria` 里有 `expected_states` 和 `overall_rubrics`，每个任务平均约 13 条 state rubric。

3. **模拟用户派发任务**
   
   论文里的 user simulator 有几个关键规则，很值得借鉴：
   
   - 不一次性暴露所有需求，而是多轮逐步说。
   - 只有 agent 主动问到时，才暴露隐含约束。
   - 有 persona，比如急躁、依赖、冷淡、细节控。
   - 如果 prompt 里没有的信息，模拟用户必须说“不知道”，不能编。
   - 任务未完成前不主动结束对话。

   这对测 agent 的主动澄清非常重要。比如用户只说“帮我重新规划下午行程”，agent 应该问当前位置、时间预算、偏好，而不是直接瞎排。

4. **Rubric-based Sliding Window Evaluator**
   
   这是最值得借鉴的评估器方法。

   做法是：把完整对话轨迹按窗口切开，比如论文附录里是 **10 turns 一个窗口，窗口之间 overlap 2 turns**。Evaluator 维护一个 rubric 状态表：

   ```json
   {
     "rubric_key": "hotel_nearest_city_gov",
     "rubric": "酒店需要选择距离南阳市政府最近的全季酒店",
     "meetExpectation": true,
     "justification": "agent 查询并选择了最近的目标酒店"
   }
   ```

   每个窗口只更新相关 rubric。某个 rubric 一旦完成就保持 true，除非后面 agent 明确推翻了之前正确结果。

   这个方法比“只看最终数据库状态”更强，因为它能评：
   
   - agent 有没有主动澄清；
   - 是否正确推荐但没有下单；
   - 是否工具调对了但最终解释错了；
   - 是否中途遗漏用户约束；
   - 是否误以为下单成功，但工具返回其实失败。

5. **最终分数很严格，但中间信号很细**
   
   VitaBench 主结果采用 all-or-nothing：

   - 所有 rubrics 都满足，任务成功。
   - 只要漏一个关键 rubric，任务失败。

   但它同时保留每条 rubric 的完成情况，用来做错误分析。你做自己的测评时建议同时输出：
   
   - `strict_success`: 是否全满足。
   - `rubric_score`: 完成 rubrics / 总 rubrics。
   - `tool_success`: 工具调用和参数是否正确。
   - `interaction_score`: 是否主动澄清、是否记住用户偏好。
   - `final_response_score`: 最终摘要是否完整、无幻觉。

6. **多次运行指标**
   
   论文不是每题只跑一次，而是每个任务跑 4 次，然后报告：

   - **Avg@4**：4 次平均成功率。
   - **Pass@4**：4 次里至少成功一次。
   - **Pass^4**：4 次全部成功。

   这个很有用。`Pass@4` 看“有没有可能做对”，`Pass^4` 看“稳不稳定”。对 agent 测评来说，稳定性非常关键。

7. **消融实验也可以借鉴**
   
   论文比较了三种交互设置：

   - default user：带 persona 的模拟用户。
   - neutral user：中性用户。
   - solo agent：一次性给完整任务，不做多轮用户交互。

   你可以用这个区分：agent 是不会做任务，还是不会和用户互动。

**我建议你借鉴的落地版本**

对你的 travel agent，第一版可以这样做：

1. 任务集：先选 20-50 个 OTA/travel 任务，覆盖重排、天气分支、距离约束、酒店/景点/交通组合、突发变更。
2. 每题写 atomic rubrics，不只写 expected final state。
3. 加一个模拟用户，让需求逐步暴露，并测试 agent 是否主动澄清。
4. 保存完整 trajectory：用户消息、agent 回复、tool call、tool result、状态变化。
5. 用 sliding-window evaluator 给每条 rubric 更新 true/false。
6. 每题至少跑 4 次，报告 `Avg@4 / Pass@4 / Pass^4`。
7. 失败后按三类归因：推理错误、工具错误、交互错误。

最关键的一点：不要只测“最后有没有给出一个计划”。要测 agent 在过程中是否正确获取信息、调用工具、处理约束、完成状态变更，并且能不能稳定复现。
