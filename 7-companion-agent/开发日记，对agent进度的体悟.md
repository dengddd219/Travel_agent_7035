# 开发日记：对 Agent 进度的体悟

## 1. 现在做到哪里了

这一轮开发里，我逐渐意识到，当前系统还不能算“完成态的 Agent”，更准确地说，它是：

> 一个正在成形的 Agent 骨架，加上一套用 Python 写的工具层和护栏层。

也就是说，现在的系统已经具备了一些 Agent 雏形：

- 有多轮状态，而不是单轮问答
- 有任务编排，会区分 search / coordinate / replan / emergency
- 有工具调用链，可以接地图、天气、POI、应急查询
- 有自然语言入口，用户不是在调函数，而是在说模糊的人话

但与此同时，它也还明显带有“工具编排程序”的味道：

- 规则很多
- fallback 流很重
- 真正由 LLM 主导的部分还没有跑起来

所以当前阶段不应该自欺欺人地说“已经做成了 Agent”，而应该说：

> 系统正处在从“普通 Python 工具流”走向“真正 Agent 架构”的过渡阶段。

---

## 2. 什么是 Agent，什么不是

开发过程中我反复在问一个问题：

> Agent 难道就是写很多 if 判断吗？

答案当然不是。

真正的 Agent 价值，不应该体现在“写了很多 Python 代码”，而应该体现在以下几件事情上：

### 2.1 理解自然语言

用户不会说结构化指令，只会说：

- “老人走不动了”
- “天安门广场不想淋雨”
- “找个吃饭的，小孩不吃辣，预算高一点”

Agent 的价值，是把这些自然语言转成结构化约束、目标和状态变化。

### 2.2 自动规划行动步骤

一条人话背后，系统应该能自动拆成一串动作：

- 先定位
- 再查候选
- 再算路线
- 再判断是否来得及
- 再决定是否需要重规划
- 最后给出答复

这一步体现的是 Agent 的 orchestration 能力，而不是单个工具的能力。

### 2.3 跨信息源做协调

单独的地图搜索做不到：

- 当前在哪
- 后面还要去哪
- 带老人还是带小孩
- 下没下雨
- 用户不想吃什么
- 这个点是不是来得及

Agent 的价值，恰恰在于把这些约束协调起来。

### 2.4 在不确定环境下还能推进

真实世界里数据会缺、工具会失败、景区内设施也可能搜不到。

如果系统还能继续给出“保守但可执行”的建议，这才有一点智能体的味道。

---

## 3. 为什么现在系统里还会有很多规则

虽然 Agent 不等于写规则，但落地时又不能把一切都交给模型自由发挥。

有些问题如果完全交给 LLM，输出会非常不稳定，例如：

- 时间计算
- 路线是否赶得上
- 已经否定的目标不能再推回来
- 下雨时不能再推荐明显室外点位
- 医疗和应急场景不能给轻率建议

因此一个更成熟的结构应该是：

> LLM 负责理解和规划  
> 规则/算法负责约束和校验  
> API 负责提供实时世界信息

所以，规则不是 Agent 的本体，而是护栏。

问题不在于“有没有护栏”，而在于：

> 护栏不能取代大脑。

我在这轮开发里逐渐意识到，当前系统的现状正是：

- 护栏很多
- 大脑还不够强

这个判断是准确的。

---

## 4. fallback deterministic flow 到底是什么

当前开发中一个非常关键的现实问题是：

> LLM 的 tool-calling 主链路并没有真正跑通。

因为 Azure / Foundry 端的 `api-version` 问题，真实的 LLM agent flow 一直没正常接起来。

所以当前 smoke test 能跑通，靠的是：

> fallback deterministic flow

它的意思是：

> 当真正的 LLM Agent 流程跑不通时，系统退回到一套“写死规则、可预测执行”的备用流程。

理想流程本来应该是：

```text
用户输入
→ LLM 理解问题
→ LLM 决定调用哪些工具
→ 工具执行
→ LLM 汇总回复
```

但当前实际运行的是：

```text
用户输入
→ Python 用规则判断 intent
→ Python 直接调工具
→ Python 做排序 / 时间判断
→ Python 拼一个回复
```

所以现在的系统虽然“能跑”，但并不等于“已经是一个成熟的 Agent”。

它只是：

> 一个可以工作的 fallback baseline。

---

## 5. 这一轮暴露出的三类问题

这一轮最大的收获，不是“做成了 Agent”，而是通过 fallback flow 把关键问题暴露出来了。

这些问题大致可以分成三类。

### 5.1 业务逻辑问题

这类问题的特点是：

> 就算不用 LLM，只靠人工写程序，也应该被正确处理。

这次典型暴露出来的业务逻辑问题包括：

#### 地点歧义处理不完善

- `王府井` 一开始被解析成了洛阳，不是北京。
- 这说明地点解析必须有 `city bias`，不能裸查关键词。

#### 时间可行性判断过于粗糙

- 一开始只算了“路上多久”，没算景点游玩时长。
- 后来又发现，即使加了景点时长，还要考虑老人、小孩、下午体力下降。

也就是说，“可行性”不是路线时间，而是：

- 路线时间
- 景点建议游玩时长
- 闭园时间
- 老人 / 小孩的体力负担

#### 用户明确否定的目标没有进入硬约束

- 用户说“天安门广场不想淋雨”，系统却还能推荐天安门。
- 说明需要正式引入：
  - `avoid_pois`
  - `prefer_indoor`

#### 应急搜索不能只依赖单个关键词

- 直接搜“休息区 / 医院 / 药店”不够稳。
- 后来才逐渐改成“场景 → 场所 → 搜索词”的映射方式。

#### 多轮状态还不够结构化

系统虽然能记住“我在王府井”，但还不能很稳定地把以下内容变成长期约束：

- 下雨了
- 不想去某个点了
- 带老人小孩
- 当前位置已经切到颐和园

这说明状态层还需要升级。

可以总结为一句话：

> 当前暴露出的核心业务问题，不是“模型不够聪明”，而是地点歧义、时间可行性、硬约束继承、应急场景映射和结构化状态设计还不够完整。

---

### 5.2 Agent 感不足

这类问题的特点是：

> 系统虽然能输出结果，但不像一个“会思考、会协调、会持续跟进”的智能体，更像一个规则脚本。

这一轮最明显的 Agent 感不足包括：

#### 意图判断太像手写分流

目前主要还是 Python 在判：

- search
- coordinate
- replan
- emergency

这更像一个流程机，而不是 Agent 在理解任务。

#### 工具链不是模型主动规划的

现在多数时候不是模型自己决定：

- 先查位置
- 再查候选
- 再查路线
- 再重规划

而是 fallback flow 里写好的固定顺序。

#### 输出会给结论，但不像人一样解释决策

比如早期只会说“整体可行”，却不会说明：

- 为什么可行
- 为什么不可行
- 如果不可行，替代方案是什么

真正的 Companion Agent 不该只是下判断，还应该给可执行替代方案。

#### 约束继承不够稳定

用户说“下雨了不想去天安门广场”，系统一开始只是局部修补，而不是正式更新任务状态。

这说明它更像“本轮问答处理器”，还不像“持续陪伴式决策体”。

#### 主动性不足

当前系统主要还是“你问一句我答一句”。

真正的 Companion Agent 应该会主动补充：

- “这组安排偏赶”
- “老人同行建议减少一个大景点”
- “下雨时建议直接切室内”

总结一句：

> 当前系统已经有 Agent 的外壳，但主体仍偏规则驱动的工具编排程序，缺少由模型主导的任务理解、工具规划、约束继承和主动建议能力，因此 Agent 感不足。

---

### 5.3 LLM 没接通导致只能走 fallback

这类问题的特点是：

> 不是业务规则没想清楚，而是原本该由 LLM 完成的部分，现在被 Python 备用流顶上了。

最明确的证据就是：

#### tool-calling 一直报错

错误一直是：

- `Missing required query parameter: api-version`

说明真实的 Azure / Foundry tool-calling 主链并没有跑起来。

#### 主流程实际上不是模型规划，而是本地规则流

所以当前 smoke test 虽然能跑通，但跑通的不是“真 Agent 流程”，而是 fallback 流程。

#### 语义理解没有真正交给模型

原本应该由 LLM 负责的内容，包括：

- 从自然语言抽取结构化约束
- 规划本轮工具链
- 汇总工具结果生成自然语言答复

而现在很多工作都由 Python 规则承担了。

#### 当前结果不能代表最终 Agent 形态

这一版的价值是：

- 验证业务逻辑
- 收集失败模式
- 清理防蠢边界

但不能把它误当成“最终的 Agent 效果”。

#### fallback 不能无限打补丁

fallback 的作用是：

- 先跑通
- 先别太蠢

而不是无限堆规则把系统做成传统程序。

总结一句：

> 当前系统之所以大量依赖规则和固定流程，并不是因为 Agent 天生如此，而是因为真实的 LLM tool-calling 主链尚未接通，导致系统只能依赖 fallback deterministic flow 来完成主要任务。

---

## 6. 当前所处阶段

结合整个开发过程来看，我认为这个项目目前处在：

> 阶段 2：Fallback Deterministic Flow 的后半段

也就是说：

- 方案已经收敛
- 骨架已经搭起来
- smoke test 已经能跑
- 当前重点不再是“有没有系统”，而是：

> 通过 fallback flow 暴露并修正旅行 Companion 场景中的关键愚蠢错误

这一步的目标不是更智能，而是更合理。

这一步的价值在于：

- 弄清楚系统最容易在哪些地方犯蠢
- 把业务逻辑中真正关键的约束摸清楚
- 让后续 LLM 接入时有明确护栏，而不是盲试 prompt

所以当前阶段不是浪费时间，而是在做：

> 业务护栏建模 + 真实失败模式收集

---

## 7. 下一步该做什么

如果继续开发，下一步不应该继续无止境修 patch。

下一步真正重要的是进入：

## 阶段 3A：结构化约束层

也就是正式把当前反复暴露出来的经验，抽象成结构化状态和约束。

最关键的字段应该包括：

- `intent`
- `current_location`
- `avoid_pois`
- `prefer_indoor`
- `party`
- `budget_level`
- `food_constraints`
- `mobility_risk`
- `weather_suitability`

换句话说，下一步应该做的不是“继续堆很多 if”，而是：

> 把现在 fallback 里积累出来的经验，提升为统一的状态模型和约束模型。

只有这样，系统才会从：

- 补丁式修正

走向：

- 真正的 Agent 化

---

## 8. 最后的判断

这一轮开发最大的体会是：

> 当前我做的，还不是“Agent 已经成了”，而是在把它从普通 Python 工具流，往真正的 Agent 架构上推。

因此：

- 现在它的价值主要还体现在骨架和护栏上
- 真正的智能性还没有充分释放
- 继续做下去的关键，不是再修更多 if
- 而是尽快进入“结构化约束层 + 真正 LLM 工具规划”的阶段

可以用一句话概括当前状态：

> 现在这个系统已经有了 Agent 的方向，但还没有完全具备 Agent 的灵魂。
