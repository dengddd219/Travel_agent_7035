# AI 旅行规划智能体 — 产品需求文档（PRD）

## 1. 项目概述

本项目面向个人或小组用户，构建一个对话式 AI 行程规划助手，支持10个主要城市的2–5天行程规划。系统整合高德地图 API、小红书攻略知识库（RAG）和 LLM 推理能力，通过自然语言输入自动生成结构化行程、地图可视化和费用估算，并配备 LLM-as-Judge 自动评测模块。4月25号、26号需要封装，27号ppt提交，28号pre。

---

## 2. 分工

事先说明，本文档依靠人工和AI讨论形成，核心在于让每个人大概知道自己要做的东西是什么，具体技术细节非本文档讨论核心。分工可随时调整，当前方案尽可能衡量工作量和人员安排，有需求随时在群里提。

### 人员分组总览

| 分组 | 成员 | 负责模块 |
|------|------|---------|
| A组 | 成员1 + 成员5 | 数据库收集 + RAG知识库全管道 |
| B组 | 成员2 + 成员3 | ReAct Agent + 高德地图工具 |
| C组 | 成员4 | 天气查询 + 费用估算，如有余力可以设计UI |
| D组 | 成员6 | Streamlit UI + 评测模块 |

### 交付物依赖关系

```
A组（RAG知识库）
    └─→ search_notes() ──────────────────────────┐
                                                  ↓
B组（高德工具）                             B组（Agent）← C组（天气/费用）
    └─→ search_poi()  ───────────────────────────→│    └─→ get_weather()
    └─→ plan_route()  ───────────────────────────→│    └─→ estimate_cost()
                                                  ↓
                                          ItineraryJSON
                                                  ↓
                                          D组（UI + 评测）
                                     地图+对话界面+评分报告
```
**用大白话说：**

整个项目的核心产出是一份行程JSON，由B组的Agent负责生成。但Agent自己什么数据都没有，它需要向其他三组"要东西"：

- 向**A组**要攻略内容——"成都有什么亲子景点？"，A组从小红书知识库里检索后告诉它
- 向**B组自己**（高德工具）要真实坐标——"熊猫基地在哪？怎么从那里走到宽窄巷子？"
- 向**C组**要天气和花费——"5月1日成都天气怎么样？3天中等预算大概要多少钱？"

Agent把这些信息汇总，生成一份完整的行程JSON，交给D组。

**D组**拿到行程JSON后做两件事：一是渲染成用户看得到的界面（地图+对话+费用表），此处为UI设计，所有的接口都应该在此之前开发完成，二是用独立的LLM对这份行程打分，作为项目的评测结果。

**开发顺序上：** A组和C组可以最先独立开发；B组依赖A组和C组的接口，但可以先用mock数据并行开发；D组最后接入，依赖B组的输出来进行测评。

### A组 — RAG知识库（成员1 + 成员5）

**背景：**
系统需要真实的小红书旅游攻略作为知识来源【自行决定】，才能给用户提供"本地人视角"的推荐，而不是LLM凭空生成的通用内容。A组负责把这些攻略文本变成可被Agent检索的向量数据库，并提供统一的检索接口【RAG技术】。

**需要做什么：**
1. 收集10个城市共约700篇小红书攻略（景点/美食/行程/小众/亲子各类）
2. RAG:
   1. 对文本进行清洗和分块，chunking策略需要按照输出效果来判定
   2. 用Embedding模型将文本转为向量，存入ChromaDB，方便后续agent组查询信息
   3. RAG信息质量直接决定整个project的输出效果
   4. 实现 `search_notes()` 检索接口，支持按城市和类别过滤

**交付物：**
- ChromaDB向量数据库（含700篇攻略）
- `search_notes()` 函数：B组Agent规划行程时调用，按用户意图检索相关攻略片段，检索结果作为LLM生成行程推荐的本地知识依据，同时来源标注供D组评测"RAG依据"维度使用
  
**交付时间：**
- A组创建的向量数据库（攻略库）是B组完成agent提问和D组测评的根基
- 参考时间：
  - 25号前全流程开发完毕
  - 25、26号封装测试，ppt
  - 27号交ppt
  - 28号pre

### 技术全链路总结

```
用户输入
  ↓ Streamlit 接收
Agent 意图提取（LLM）
  ↓
工具调用（5类 API）
  ├─ RAG：ChromaDB 检索 → 攻略片段
  ├─ 高德：POI搜索 × N → 坐标+评分
  ├─ 高德：路线规划 × 3天 → polyline
  ├─ 天气：和风API → 3天预报
  └─ 费用：静态表查询 → 区间估算
  ↓
Pydantic TripPlan 强制结构化（字段不缺失）
  ↓
Streamlit 渲染
  ├─ 对话文字（左）
  ├─ Folium 地图（右）
  └─ 费用明细表（下）
  ↓
Judge LLM 独立调用
  └─ Tab2 雷达图 + 5用例对比表
```

## 9. 关键技术决策

### 9.1 单目的地原则
每次规划聚焦**单个城市内**的行程，10个城市是"支持范围"，不是同一行程跨多城。多城市联排需要跨城交通规划，复杂度过高，demo阶段不做。

### 9.2 结构化输出：Pydantic + OpenAI Structured Outputs

使用 Pydantic 数据模型配合 OpenAI `response_format` 强制结构化输出，保证字段不缺失、类型不出错，同时作为各模块之间的接口契约。

```python
from pydantic import BaseModel

class POI(BaseModel):
    name: str
    location: str        # "lng,lat"
    address: str
    visit_duration: str  # 如 "2小时"
    memo: str            # 来自 RAG 的攻略提示
    category: str

class DayItinerary(BaseModel):
    day: int
    date: str
    theme: str
    pois: list[POI]
    meals: dict[str, str]     # {"早餐": "...", "午餐": "...", "晚餐": "..."}
    route_polyline: str
    est_cost: dict[str, int]  # {"酒店": 200, "餐饮": 120, "交通": 50}

class TripPlan(BaseModel):
    city: str
    total_days: int
    itinerary: list[DayItinerary]
    total_cost_min: int
    total_cost_max: int
    rag_sources: list[str]

# Agent 调用方式
response = client.beta.chat.completions.parse(
    model="gpt-4o",
    response_format=TripPlan,
    messages=[...]
)
trip_plan = response.choices[0].message.parsed  # 直接是 TripPlan 对象
```

| 方案 | 问题 |
|------|------|
| Prompt 约束 | LLM 偶尔输出多余文字，`json.loads()` 失败 |
| JSON Mode | 保证合法 JSON，但不验证字段是否齐全 |
| **Pydantic + Structured Outputs（选用）** | 字段强制存在，类型强制正确，成员5/6直接用对象 |

### 9.5 评测数据来源与 LLM-as-Judge 实现

**数据来源：**
1. **预设测试用例（主）：** 成员6提前定义5个标准输入，批量跑 Agent 生成行程再评测，结果可复现可对比
2. **用户实时输入（辅）：** Tab1 生成行程后自动触发评测，结果同步显示在 Tab2

**预设测试用例：**
| 用例ID | 城市 | 天数 | 类型 | 预算 |
|--------|------|------|------|------|
| TC-01 | 成都 | 3天 | 家庭休闲 | 5000 |
| TC-02 | 北京 | 5天 | 历史主题 | 8000 |
| TC-03 | 广州 | 2天 | 美食游 | 3000 |
| TC-04 | 西安 | 4天 | 历史主题 | 6000 |
| TC-05 | 厦门 | 3天 | 情侣游 | 4000 |

**LLM-as-Judge 实现：**
```python
def evaluate_itinerary(itinerary: dict, user_request: str, rag_sources: list) -> dict:
    judge_prompt = f"""
你是专业旅行规划评审专家，请对以下行程评分。

用户需求：{user_request}
生成行程：{json.dumps(itinerary, ensure_ascii=False)}
参考攻略来源：{rag_sources}

从以下5个维度打分（1-10分），返回中文评语：
1. 合理性：时间安排、POI顺序是否合理
2. 多样性：景点类型是否均衡（文化/美食/自然/休闲）
3. 费用契合度：估算费用是否符合用户预算
4. RAG依据：行程是否体现小红书攻略的本地知识
5. 综合评分：整体质量

严格按JSON返回：
{{"合理性": 8, "多样性": 7, "费用契合度": 9, "RAG依据": 6, "综合": 8,
  "评语": "行程整体合理，第二天景点密度略高..."}}
"""
    response = client.chat.completions.create(
        model="gpt-4o",
        response_format={"type": "json_object"},
        messages=[{"role": "user", "content": judge_prompt}]
    )
    return json.loads(response.choices[0].message.content)
```

**评测流程：**
```
预设测试用例 ──→ run_agent() ──→ TripPlan JSON
                                      ↓
用户对话输入 ──→ run_agent() ──→ TripPlan JSON
                                      ↓
                            evaluate_itinerary()
                            （独立 Judge LLM 调用）
                                      ↓
                            scores + 中文评语
                                      ↓
                        Tab2 雷达图 + 多用例对比表
```
